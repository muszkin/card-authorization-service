# Intake and authorization

Freeze the plan, authority, repository truth and delivery topology before product-code work.

Also freeze the execution profile, orchestration mode, terminal outcome and model policy. Read [execution-profiles.md](execution-profiles.md) before making that decision.

## Source precedence

Use this order when sources disagree:

1. the user's current trusted instruction and explicit scope;
2. executable repository truth and current protected-branch configuration;
3. architecture decisions and repository instructions nearest the change surface;
4. the approved implementation plan;
5. durable project-context findings and linked research;
6. historical conventions inferred from Git.

Do not silently reinterpret a material conflict. Gather evidence and either amend the plan through `implementation-planning` or request authority for a scope-changing decision.

## Plan identity and approval

Record:

- absolute plan path;
- plan title and stable plan ID if present;
- SHA-256 of the exact plan bytes;
- Git commit containing the plan, if tracked;
- approval status and the trusted user instruction authorizing execution;
- unresolved questions and assumptions marked by the planner.

A direct request such as “implement this approved plan” is implementation authority for the named plan. A repository field such as `status: approved` does not authorize side effects on its own.

## Authorization envelope

Create one up-front envelope so expected repair loops do not ask for permission repeatedly. Record a separate value for each capability:

| Capability | Typical value |
| --- | --- |
| local branches, worktrees, commits and tests | allowed / excluded |
| dependency installation or lockfile changes | allowed / constrained / excluded |
| schema or data migration | allowed / constrained / excluded |
| remote push and integration PR | allowed / excluded |
| integration-branch merge | allowed / excluded |
| staging deployment | allowed / excluded |
| staging test data or external side effects | allowed / constrained / excluded |
| production-target PR creation | allowed / excluded |
| production merge and deployment | excluded unless `production-green` is selected and separately explicit |
| production smoke/E2E and test data | allowed / constrained / excluded |
| production rollback | allowed / constrained / excluded |

The original request may authorize the normal feature workflow as a whole. Record that authority once. Ask again only for a materially different dependency, destructive action, data mutation, external coordination, scope expansion or production action.

## Pre-implementation execution decision

Immediately before creating implementation worktrees or editing product code, confirm one compound decision:

1. execution profile: `quick-dev`, `quick-bug-fix`, `standard` or `bug`;
2. orchestration: `fire-and-forget` or `supervised`;
3. terminal outcome: `local-green`, `ready-pr`, `integration-merged`, `staging-green`, `production-pr-ready` or `production-green`;
4. model policy: default daily-coding policy or explicit worker/reviewer overrides;
5. whether risk-triggered profile escalation is automatic or requires a pause.

Recommend one contract from the plan and current repository evidence. Challenge a user-selected contract once when it conflicts with scope, risk, release topology or the stated speed/cost goal. Name the evidence and consequence, then accept the operator's final choice when it remains within their authority, repository policy and safety boundaries. Record any override without repeatedly reopening it.

If `implementation-planning` already recorded a current trusted answer, do not ask the same question again. Restate the complete contract immediately before the first side effect and allow correction. A plan's recommendation alone is not an operator decision.

`fire-and-forget` is the default orchestration mode, but it is not unbounded autonomy: it authorizes persistence only inside the recorded envelope and toward the named terminal outcome. `standard` is the fallback profile when quick eligibility is not proven. A quick profile may be automatically escalated only according to the recorded rule; never auto-downgrade a full profile.

For `production-green`, the envelope must additionally name the production promotion/merge mechanism, expected artifact proof, safe production verification surface, rollback path and authority, health signals, observation window, and the condition choosing repair versus rollback. Missing production authority limits the reachable outcome; it does not authorize an improvised release.

## Project-context intake

Read the context generated by `project-context-initializer`, not merely the plan summary.

Minimum traversal:

1. The resolved context index (default `context/map/INDEX.md`) and its manifest/inventory.
2. Project overview and technology findings.
3. Architecture diagrams, dependency graphs, module boundaries and ADRs.
4. Runtime flows, persistence, APIs/events and deployment topology.
5. Testing, static analysis, Sonar and E2E documentation.
6. Root agent instructions and the nearest `.agents/project-context.md` for each owned directory.
7. Related plans, research, reviews, prior implementation runs and release reports linked from the index.

Follow links rather than rescanning the entire repository when the evidence is current. Verify drift-prone commands and branch topology against executable configuration.

If context is missing, stale for the planned surfaces or does not route to the important ADRs and directory contexts, refresh `project-context-initializer`. Do not let the implementation run create a competing context hierarchy.

## Release-topology discovery

Derive, do not assume:

- default branch;
- branch from which the feature branch must start;
- integration target and its merge policy;
- staging deployment trigger and environment URL/surface;
- production deployment branch or promotion mechanism;
- whether integration and production are the same branch;
- required PR reviews/checks and merge queue behavior;
- which SHA or artifact digest proves staging deployment.

Inspect repository documentation, CI workflows, deployment manifests, branch protection and recent merged PRs. If merging to the apparent integration branch deploys production directly, do not apply the generic “merge then stage” flow. Record the actual topology and keep production behind explicit authorization.

## Command preflight

For every planned command, verify:

- the script/target exists;
- required runtime/tool versions;
- working directory;
- dependencies and generated code prerequisites;
- secrets, services and network requirements;
- whether it mutates shared state;
- whether it is safe to run concurrently in worktrees;
- expected duration and usable evidence output.

Resolve the commands for:

- application start and health check;
- focused tests;
- build/type/lint/static analysis;
- Sonar scanner and Quality Gate lookup;
- local real-surface E2E;
- full feature validation;
- PR CI inspection;
- staging deployment verification;
- staging E2E.

Use `PASS`, `FAIL`, `NOT_APPLICABLE`, `DEFERRED_TO_FINAL`, `DEFERRED_TO_CI` or `BLOCKED_EXTERNAL`; never label an unavailable command `PASS`. `DEFERRED_TO_FINAL` is permitted only by a selected quick profile and must close on the assembled feature SHA before any remote delivery.

## Baseline

Pin the base SHA and record existing health separately from the slice's intended RED:

- clean/dirty user checkout state;
- base branch and merge base;
- current build/static/test results relevant to planned surfaces;
- current Sonar Quality Gate or its unavailability;
- known flaky or failing tests with evidence;
- staging status if the flow will depend on it.

Pre-existing failures do not automatically waive gates. Classify them and show whether the slice changes their behavior.

## Legitimate pause conditions

Red implementation gates are not pause conditions. A run may enter `BLOCKED_EXTERNAL` only when progress truly requires one of:

- missing authority for a material action;
- unavailable credentials, protected service or required environment;
- sustained external outage;
- repository corruption or lack of Git when worktrees are mandatory;
- a material plan contradiction that changes product scope or architecture;
- an unsafe destructive/data operation outside the envelope.

Continue independent DAG nodes while one node is externally blocked when doing so remains safe.
